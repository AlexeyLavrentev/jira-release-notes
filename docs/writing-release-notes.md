# Как заполнять поле Release Note

Этот гайд — **для инженеров**, закрывающих задачи. Текст, который вы пишете в поле Release Note,
попадает в итоговый документ release notes как есть (FIELD-02): без автогенерации, без
перефразирования. Качество release notes целиком зависит от вашей дисциплины заполнения.

Как завести само поле в Jira (для администратора) — см.
[docs/jira-field-setup.md](jira-field-setup.md).

## Формат

Поле заполняется **plain text или markdown**.

НЕ Jira wiki markup. Не используйте `{code}`, `{color}`, `{noformat}`, заголовки `h1.`/`h2.` и
прочий Jira wiki-синтаксис — приложение рендерит заметку как markdown в live preview и экспортирует
её в Markdown/plain text/HTML. Wiki markup останется в выгрузке сырым текстом вроде `{code}...{code}`.

Допустимо: обычный текст, markdown-разметка (жирный, списки, инлайн-код, ссылки).

## Примеры

| Заметка | Оценка | Почему |
|---------|--------|--------|
| `bugfix` | Плохо | Плейсхолдер — не говорит, что изменилось. Приложение пометит как заглушку. |
| `фикс` | Плохо | То же самое: приложение распознаёт как плейсхолдер/короткий текст. |
| `мелкие правки` | Плохо | Размыто. Читатель release notes не поймёт, что именно поменялось. |
| `Исправлен краш при открытии отчёта на пустых данных` | Хорошо | Конкретное действие + условие, при котором проявлялся баг. |
| `Добавлен экспорт release notes в HTML (с sanitize от XSS)` | Хорошо | Что добавлено + значимая техническая деталь. |
| `Обновлён Node до 22 LTS; удалён устаревший эндпоинт /api/v1/issues` | Хорошо | Markdown через `;` укладывает несколько пунктов в одно поле. |

Главный принцип: заметка должна описывать **ЧТО изменилось** для пользователя или системы —
достаточно конкретно, чтобы читатель release notes понял суть без открытия самого issue.

## Что приложение считает проблемным заполнением

Приложение проверяет содержимое поля и подсвечивает три категории проблем (VALID-01..03). Эти
задачи **не исключаются** из списка — предупреждение означает «обрати внимание», а не «скрыто».

- **[ПУСТО]** — поле не заполнено (`releaseNote === ""`, VALID-01). Помечается предупреждением.
- **[КОРОТКО]** — меньше 15 символов (VALID-02). Слишком короткая заметка обычно бесполезна.
- **[ЗАГЛУШКА]** — текст распознан как плейсхолдер (VALID-02). Распознаются case-insensitive
  (после обрезки пробелов): `n/a`, `na`, `todo`, `tbd`, `без комментария`, `нет описания`, `нет`,
  `---`, `...`, `заглушка`, `placeholder`, `bugfix`, `фикс`, `исправлено`, `fixed`, `разное`, а
  также строки, состоящие только из цифр/дефисов/точек.

Подсвеченные задачи остаются в списке (VALID-03) — инженер может отредактировать заметку прямо в
приложении перед экспортом.

## Чек-лист перед релизом

- [ ] У каждой закрытой задачи заполнено поле Release Note
- [ ] Заметка описывает, **ЧТО изменилось** для пользователя/системы (не «багфикс»)
- [ ] Заметка укладывается в 1–2 строки (длинные описания — в самом issue)
- [ ] Если заметок несколько в одном поле — они разделены `;` или новой строкой (markdown-списком)
- [ ] Нет Jira wiki markup

## Подсказки по markdown

| Разметка | Результат |
|----------|-----------|
| `**важное слово**` | **важное слово** (жирный) |
| `- пункт` | элемент маркированного списка |
| `1. пункт` | элемент нумерованного списка |
| `` `customfield_10000` `` | `customfield_10000` (инлайн-код) |
| `[текст](url)` | гиперссылка |

Markdown удобен, когда в одном поле нужно уместить несколько пунктов:

```
- Добавлен экспорт в HTML
- Исправлен краш на пустых данных
- Обновлён Node до 22 LTS
```
