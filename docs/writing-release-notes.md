# Как заполнять поле Release Note

Этот гайд — **для инженеров**, закрывающих задачи. Текст, который вы пишете в поле Release Note,
попадает в итоговый документ release notes как есть (FIELD-02): без автогенерации, без
перефразирования. Качество release notes целиком зависит от вашей дисциплины заполнения.

Как завести само поле в Jira (для администратора) — см.
[docs/jira-field-setup.md](jira-field-setup.md).

## Формат

Поле заполняется **plain text или markdown**.

НЕ Jira wiki markup. Не используйте `{code}`, `{color}`, `{noformat}`, заголовки `h1.`/`h2.` и
прочий Jira wiki-синтаксис — приложение рендерит заметку как markdown в live preview и экспортирует
её в Markdown/plain text/HTML. Wiki markup останется в выгрузке сырым текстом вроде `{code}...{code}`.

Допустимо: обычный текст, markdown-разметка (жирный, списки, инлайн-код, ссылки).

## Примеры

| Заметка | Оценка | Почему |
|---------|--------|--------|
| `bugfix` | Плохо | Плейсхолдер — не говорит, что изменилось. Приложение пометит как заглушку. |
| `фикс` | Плохо | То же самое: приложение распознаёт как плейсхолдер/короткий текст. |
| `мелкие правки` | Плохо | Размыто. Читатель release notes не поймёт, что именно поменялось. |
| `Исправлен краш при открытии отчёта на пустых данных` | Хорошо | Конкретное действие + условие, при котором проявлялся баг. |
| `Добавлен экспорт release notes в HTML (с sanitize от XSS)` | Хорошо | Что добавлено + значимая техническая деталь. |
| `Обновлён Node до 22 LTS; удалён устаревший эндпоинт /api/v1/issues` | Хорошо | Markdown через `;` укладывает несколько пунктов в одно поле. |

Главный принцип: заметка должна описывать **ЧТО изменилось** для пользователя или системы —
достаточно конкретно, чтобы читатель release notes понял суть без открытия самого issue.

## Что приложение считает проблемным заполнением

Приложение проверяет содержимое поля и выделяет три категории проблем (VALID-01..03). Такие задачи
**не попадают в тело документа** с предупреждением — вместо этого они уходят в отдельную секцию
**«Нет release note»** в конце экспортируемого файла (и в DocumentPreview), где перечислены ключ,
summary и человекочитаемая категория проблемы. Так автор сразу видит, что именно осталось дозаполнить.

- **[пусто]** — поле не заполнено (`releaseNote === ""`, VALID-01). Категория для пустых заметок.
- **[коротко]** — заметка короче порога (по умолчанию 15 символов, VALID-02). Слишком короткая
  заметка обычно бесполезна читателю.
- **[заполнение]** — текст распознан как плейсхолдер (VALID-02). Распознаются case-insensitive
  (после обрезки пробелов): `n/a`, `na`, `todo`, `tbd`, `без комментария`, `нет описания`, `нет`,
  `---`, `...`, `заглушка`, `placeholder`, `bugfix`, `фикс`, `исправлено`, `fixed`, `разное`, а
  также строки, состоящие только из цифр/дефисов/точек. Категория-просьба: впишите осмысленный текст.

Секция «Нет release note» присутствует во всех трёх форматах экспорта (Markdown, plain text, HTML) и
в предпросмотре — с одинаковым порядком задач и теми же lowercase-метками категорий. Тело документа
содержит только валидные release notes. Автор дозаполняет проблемные заметки прямо в приложении
перед экспортом — после правки задача автоматически уходит из секции «Нет release note» в основную
группу при следующей сборке.

### Порог короткой заметки (`shortThreshold`)

Порог, ниже которого заметка считается короткой, настраивается через `config.json`:

```json
{
  "shortThreshold": 15
}
```

По умолчанию — 15 символов. Допустимый диапазон: от 1 до 500. Изменение применяется после
перезапуска контейнера (config читается один раз при старте). Если поле отсутствует в `config.json`,
используется значение по умолчанию (15) — существующие конфиги работают без изменений.

## Пропуск задачи из release notes

Иногда задачу умышленно не нужно включать в release notes (внутренний рефакторинг, техническая
задача без пользовательского эффекта, дубликат). Для этого введите в поле Release Note ровно маркер:

```
<no-release-notes>
```

| Значение поля | Результат |
|---------------|-----------|
| `<no-release-notes>` | Задача **полностью исключена** из документа — не попадает ни в одну группу, ни в общее количество. |
| `  <NO-RELEASE-NOTES>  ` | То же — регистр и пробелы вокруг игнорируются (точное совпадение после trim и lowercase). |
| `Исправлен баг <no-release-notes>` | Не сработает — поле содержит реальный текст, задача остаётся валидной. Маркер должен быть **единственным** содержимым поля. |

Это не попадание в список «Нет release note» (как для пустых/коротких/плейсхолдерных заметок), а
полный пропуск: задача не мелькает в документе нигде. При этом она остаётся видна в таблице отбора
как серая зачёркнутая строка с иконкой 🚫 (Ban), а в редакторе — как read-only блок без текстового
поля. Так автор видит, что задача намеренно пропущена, и может убрать маркер, если он поставлен по
ошибке.

Маркер захардкожен — никаких алиасов и настраиваемых списков синонимов нет. Это осознанное решение
проекта: одно предсказуемое значение вместо разрастающегося списка исключений.

### Как вернуть пропущенную задачу

Чтобы задача снова попала в документ, уберите `<no-release-notes>` из поля и впишите осмысленный
release note. В приложении это можно сделать прямо в редакторе: удалить маркер и ввести текст —
задача сразу вернётся к редактируемому виду и попадёт в документ при следующей сборке.

## Чек-лист перед релизом

- [ ] У каждой закрытой задачи заполнено поле Release Note
- [ ] Заметка описывает, **ЧТО изменилось** для пользователя/системы (не «багфикс»)
- [ ] Заметка укладывается в 1–2 строки (длинные описания — в самом issue)
- [ ] Если заметок несколько в одном поле — они разделены `;` или новой строкой (markdown-списком)
- [ ] Нет Jira wiki markup

## Подсказки по markdown

| Разметка | Результат |
|----------|-----------|
| `**важное слово**` | **важное слово** (жирный) |
| `- пункт` | элемент маркированного списка |
| `1. пункт` | элемент нумерованного списка |
| `` `customfield_10000` `` | `customfield_10000` (инлайн-код) |
| `[текст](url)` | гиперссылка |

Markdown удобен, когда в одном поле нужно уместить несколько пунктов:

```
- Добавлен экспорт в HTML
- Исправлен краш на пустых данных
- Обновлён Node до 22 LTS
```
